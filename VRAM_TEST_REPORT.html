Behavioural Matrix (corrected)

Container has peak_vram_mb? Pressure-evicted? TTL-evicted?
No (default) No Yes — pre-existing behaviour preserved
Yes Yes (when needed) No — pressure is the only stop signal

Declaring peak_vram_mb opts the container into the pressure-based system and out of the time-based system. The sessions.default-duration and per-request session_duration are silently ignored for participants — replaced with a 100-year sentinel so the existing TTL machinery never fires for them. This matches the intent of "keep things loaded as long as there's room; only evict under pressure."

Defects found and fixed during testing

  • Initial test expectation in TestVRAM_VictimAlreadyBeingFreedIsNotPickedAgain was wrong. peak=7000 against 2000 available legitimately requires evicting both candidates (4000+4000); the test asserted a single eviction. Adjusted to peak=5000 so a single 4000 MB eviction satisfies, exposing the real property under test.
  • Golden config files in pkg/sabliercmd/testdata/ didn't include the new VRAM block. Updated all four (config_default.json, config_yaml_wanted.json, config_env_wanted.json, config_cli_wanted.json).
  • Initial design TTL-evicted participants too. Corrected per design feedback: participants now bypass TTL entirely. Implemented in pkg/sablier/instance_request.go by overriding the store-side duration to a 100-year sentinel for any state with PeakVRAMMB > 0 when VRAM management is enabled.

Integration Scenarios

Test harness: examples/opinionated-single-host/integration-tests/run.sh. Each scenario starts from a clean state (Sablier killed, sab-test-* containers removed), creates the per-scenario set, starts Sablier with --vram.enabled --vram.total-mb=8000 --vram.headroom-mb=500, then drives GET /api/strategies/blocking?names=… to trigger starts. Containers are nginx:alpine with healthchecks so Sablier can detect ready.

Container: noparti (no peak_vram_mb, no priority). session_duration=6s.

Trigger blocking start → HTTP 200 → noparti in running set. Wait 12 s. Result: running set empty. Non-participants are still subject to time-based eviction.

S2 — Single participant, no eviction PASS

Container a (peak=2000, priority=10). Trigger → HTTP 200 → a running. Trivial budget fit, no eviction.

S3 — Multiple participants fit PASS

Containers a (2000/10), b (2000/20), c (3000/30). Total declared = 7000 ≤ 7500 (8000 − 500 headroom). All three loaded simultaneously, no evictions.

S4 — Eviction by lowest priority PASS

Pre-loaded: a (2000/10), b (2000/20), c (3000/30). Used = 7000, free = 1000. Request d (peak=2500, priority=40). Need 2500+500 = 3000. Deficit = 2000. Candidates ordered by priority: a → b → c. Evicting a frees 2000. New free = 3000. Single eviction suffices.

Final running set: b, c, d. End-to-end latency for the d request: ≈ 6.45 s, mostly nginx healthcheck startup; eviction itself is sub-second.

S5 — Tie-break by oldest LastUsed PASS

Four containers, all priority=50. Sequence: load old, then new, then fresh (with 2 s gaps so LastUsed differs). Loading fresh already triggers an eviction because 3×3000 = 9000 > 8000. Sablier evicts the oldest (old).

Then load extra (4000). Need 4500; free = 8000 − 6000 = 2000. Deficit 2500. Candidates new (older) → fresh. Pick new. Frees 3000. Final running set: fresh, extra.

S6 — Refusal of impossible request PASS

Container huge (peak=20000) against budget 8000. HTTP 500 returned with body:

{
  "detail": "sab-test-huge: insufficient VRAM and no further eviction candidates: need 20500 MB (incl 500 headroom), can free at most 8000 MB",
  "status": 500,
  "title": "Internal Server Error"
}

No container started. pendingReserve not mutated (the manager refused before recording state).

S7 — Participants immune from TTL PASS

Container p (peak=2000, priority=50). session_duration=3s (deliberately short). Started successfully, then waited 10 s — well past the requested session duration. Participant still running. The TTL bypass via the 100-year sentinel works: only pressure (or external means) can stop a participant.

S8 — Non-participants don't trigger pressure PASS

Pre-loaded: p1 (4000/10), p2 (3000/50). Used = 7000. Trigger noparti (no peak). Sablier's pre-start path treats peak=0 as "no admission needed" — ensureVRAMAdmission returns nil immediately. No Plan call, no eviction.

Final running set: noparti, p1, p2.

S9 — Non-participants are immune from being evicted under pressure PASS

Pre-loaded: noparti (no peak), p1 (4000/10), p2 (3500/20). Participant total = 7500. Free = 500. Trigger newp (1000/100). Need 1500. Deficit 1000.

Candidate filter explicitly excludes peak_vram_mb=0 instances, so noparti is invisible to the eviction algorithm even with priority=0. Picks p1 (lowest priority among participants). Frees 4000.

Final running set: noparti, p2, newp. p1 evicted, noparti retained. This is the most important property for users with mixed AI / non-AI workloads on the same Sablier — only opt-in containers get pulled out from under requests.

Things not yet covered

  • Concurrent request bursts. Unit-tested via TestVRAM_ConcurrentReservesDoNotDoubleCount, but no integration-level "fire 5 simultaneous starts" scenario. Plan is fully serialised under one mutex, so a regression would be obvious; an end-to-end test would still build confidence.
  • Model-server warmup window. The pendingReserve entry is cleared when provider.InstanceStart returns. If a model server takes additional seconds after InstanceStart returns to actually load weights into VRAM, a follow-up request in that window will see available as if the new container had already consumed its peak. This is the conservative direction (no over-allocation), so it's safe, but it can cause unnecessary evictions for back-to-back requests against fast-starting / slow-loading model servers. Workaround: bump headroom_mb to absorb the overlap, or add a future --vram.warmup-grace=Ns knob.
  • Multi-victim cascade where one stop fails. If the first eviction stop succeeds but the second fails, ensureVRAMAdmission rolls back the new reservation (AbortReserve) and ConfirmFreeds the in-flight victim, but the previously-stopped victim is already gone. The user can retry; no leak. Docker's InstanceStop proved reliable enough that this didn't manifest, but a real provider integration test should cover it.
  • K8s / Swarm / Podman — only Docker exercised end-to-end. Label parsing is shared across providers (PopulateEnabledAndGroup) and the Provider interface is unchanged, so the behaviour should be portable, but a smoke test on each is worth doing before claiming generic support.
  • Valkey backend with VRAM enabled — startup correctly fails fast with ErrListUnsupported by code inspection. No live valkey run, but the path is small.

Reproducing

Prerequisites

  • Linux host with Docker installed and running.
  • Go 1.26 or newer (matches go.mod).
  • The nginx:alpine image will be pulled on first run; no other images required.
  • The scripts manage sab-test-* Docker containers — make sure no other containers with that name prefix exist on the host.

Running locally

# From the repo root:
go build -buildvcs=false -o ./bin/sablier ./cmd/sablier

cd examples/opinionated-single-host/integration-tests
./run.sh

The scripts assume Sablier is at ./bin/sablier relative to the repo root. Override with SABLIER_BIN=/path/to/sablier ./run.sh if you've built it elsewhere.

Running on a remote host

# Push the source up:
rsync -az ./ user@server.example.com:~/sablier/

# Build and test in one shot:
ssh user@server.example.com '
  cd ~/sablier
  go build -buildvcs=false -o ./bin/sablier ./cmd/sablier
  ./examples/opinionated-single-host/integration-tests/run.sh
'

Output

Each scenario prints >>> SCENARIO PASS or >>> SCENARIO FAIL. Final summary at the bottom shows totals; the script's exit code is the number of failures. Sablier itself logs to /tmp/sablier.log for post-mortem inspection.

Resetting between runs

The harness cleans up between scenarios automatically. If a run is killed mid-scenario and leaves residue, reset by hand:

# Kill any leftover sablier processes
pkill -f 'sablier start' || true

# Remove any sab-test-* containers
for c in $(docker ps -aq --filter "name=^/sab-test-"); do
  docker rm -f "$c"
done

Recommendation

Functionally correct against all designed scenarios with no observed defects in the eviction policy. Ready for code review and broader functional / load testing on a real GPU host. Two areas warrant follow-up before production:

  1. Confirm provider.InstanceStop is synchronous on every backend you use. Verified for Docker (it ContainerWaits on WaitConditionNotRunning). K8s / Swarm / Podman not verified end-to-end.
  2. Decide on the model-server warmup grace policy — keep pendingReserve until InstanceStart returns (today), or extend it via a --vram.warmup-grace=Ns config so slow-loading model servers don't get unnecessarily evicted by races.
